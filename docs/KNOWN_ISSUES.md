Các assert bất biến thật (vẫn từ chối, vẫn MANUAL_REVIEW, vẫn đúng MỘT khoản thu) đều giữ nguyên và đều xanh — đã sửa ba test file theo hướng đó.

## Vehicle field purge — consequences staff and operators must know (08/10/2026)

- **The old history is gone by design, not lost to a bug.** Migration `20261008000300` deletes every row in `audit_logs`, `vehicle_activity`, `notifications`, `customer_communications` and `message_outbox`. From the moment it is applied there is no before/after trail for anything recorded earlier, so any dispute about a past transaction has to be settled from the surviving tables (`vehicles`, `acquisitions`, `sales`, `sale_financials`, `payments`, `payment_receipts`, `vehicle_expenses`) — not from the activity feed. New events are still audited and still raise notifications normally.
- **Old clients fail closed, they do not degrade.** A PWA bundle built before the purge sends no `vehicle_type_id`; the server answers `VEHICLE_TYPE_REQUIRED` and the write never happens. The same applies to saved shorthand/CSV files in the old shape. The mitigation is a fresh deploy plus the deliberate draft-key bump (`xe_crm_draft_v2`, `xe_crm_ux_v3`), which drops locally stored drafts that still carry purged fields instead of reloading them.
- **Every existing vehicle starts in `Chưa phân loại` and there is no bulk-classification screen.** Reclassification is manual, one file at a time, from the edit form. Until staff do it, the vehicle-type filter in **Kho xe** and the showroom type filter sort most of the inventory into that single bucket. Expected: `list_vehicle_types` reports a large `vehicle_count` on the fallback row for a while.
- **The public showroom now prints the chassis number** (`biển số · số khung`) because the requirement was identity consistency across every screen. This is a deliberate trade-off with a real risk: a visitor can copy enough of a file to forge a claim of ownership. If the owner prefers plate-only on the public page, it is a one-parameter change inside the shared display helper on the showroom read path — not a redesign.
- **There is no price anywhere in the system for an unsold vehicle**, by decision rather than omission: `sale_price` originates only from the Bán xe form and is never prefilled, and `asking_price` no longer exists as a column. Staff cannot look up "what were we asking for this bike", and the showroom shows no price block. The customer-submitted `expected_price` on "Định giá xe cần bán" is the only price-like figure on the public side, and it is customer-declared, never a shop price.
- **`operation_receipts` rows written before the purge are idempotency ghosts only.** Replaying an old saved request through a rebuilt RPC reports `OPERATION_REQUEST_CONFLICT` rather than re-running the write; that is the intended fail-closed behavior, but it means an operator cannot "resend" a pre-purge request and must re-enter it.
- Deno is not installed on the current workstation, so `node scripts/check-edge-native.mjs` cannot run locally (it fails with `spawn deno ENOENT`, which is an environment gap, not a code failure). `check-edge-types.mjs` passes with local platform types; native edge resolution must be verified before any function deploy.

## Smart vehicle duplicate detection — operator notes and limits (09/10/2026)

- **Migration `20261009000200` is LOCAL/PENDING — it is NOT applied to production.** It DROPs the plain `UNIQUE(frame_number)` constraint and replaces it with a partial unique index; that operation is hard to reverse, so the release protocol (fresh same-day dump → pre-flight audit → `db push --dry-run` → push → verify) and explicit OWNER authorization are mandatory before applying. The pre-flight block fails closed (`DUPLICATE_DETECTION_PREFLIGHT_FAILED`) if existing non-cancelled FULL frames collide after character-compaction — reconcile those by hand first.
- **A repeated plate on an otherwise-new vehicle is YELLOW, not GREEN.** Two bikes genuinely cannot share a Vietnamese plate, so the form asks the staff member to confirm the list before saving (recorded in `public.vehicle_duplicate_checks`). This is soft, not a block — but it does mean a batch of synthetic fixtures with a constant placeholder plate now needs a distinct plate or an acknowledgement; the existing DB suites were updated accordingly (`scripts/test-db.mjs` gives each fixture a unique plate; `tests/db/plate-display-format.test.mjs` seeds its intentional same-plate spellings with `duplicate_ack`). Do NOT treat that fixture churn as a product regression.
- **RED is a hard block by decision, not a bug**: same plate AND same last-5, an existing FULL VIN (including a SOLD bike), or a PARTIAL↔FULL last-5 clash stop the save until the operator enters the full frame or opens the existing record. If a legitimate re-acquire of a SOLD bike must create a new receipt, that is a separate confirmed flow to design — today it routes to the existing file.
- **`frame_number` for a PARTIAL row is stored verbatim (the 5 typed characters), not padded** — `frame_compact`/`frame_last5` keep leading zeros as text. A future feature that needs the full VIN back must capture it in a later edit; there is no server-side expansion.
- **Race protection for PARTIAL rows depends entirely on `pg_advisory_xact_lock`**, because PARTIAL has no database uniqueness constraint. The behavior is only exercised on multi-session PostgreSQL (`node scripts/test-db.mjs`); PGlite is single-session and skips that case. Any refactor that removes the advisory lock from the save path silently reintroduces the double-insert window for fragment-only data.

If the composer moves, only `content.js` needs a change — the protocol version and CRM wording stay.
- **The mobile share sheet is untested on devices.** `navigator.canShare({files})` support differs across iOS Safari/Android Chrome/Samsung Internet, and the CRM can only prove it handed data to the OS (`READY_FOR_REVIEW` there means "you picked the app", never "Facebook received it"). `docs/AGENT_HANDOFF.md` "Android/iPhone … NOT TESTED — DEVICE REQUIRED" still applies to this feature.
- **Clipboard hand-off is HTTPS-only.** On an insecure origin `readShareEnv` reports `clipboard: false`, so MANUAL says "copy tay / tải ảnh" instead of claiming a copy. That branch is intentionally visible in the UI rather than silent.
- **No image persists on the device.** Shared images are signed and cached in memory for the current request only; nothing is written to localStorage/IndexedDB, so re-sharing an old draft re-signs the URLs (a draft whose vehicle photo was deleted simply reports the skipped count).
- **`npm run test:db` is currently red at HEAD for an unrelated reason.** Check 6 fails with `SALE_OWNER_CONFIRMATION_REQUIRED` raised by `private.sell_vehicle_impl` (`supabase/migrations/20261011000100_financial_provenance_privacy.sql`, commit `fb90144`), because `scripts/test-db.mjs` was not updated for the new owner-confirmation rule. This is the financial-privacy lane's work, not the Post Studio lane's; recorded here so the two are not confused.
