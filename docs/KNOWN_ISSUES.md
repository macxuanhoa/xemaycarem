- Purchase disbursements and expense settlements are not recorded separately, so reconciliation excludes those flows.
- Direct XLSX import is not implemented; export the spreadsheet as CSV UTF-8.

After the 08/10/2026 field purge there is no engine-number column at all, so `validate_import_vehicles` compares only `frame_number` and `license_plate` (migration `20261008000300`, duplicate loop over `ARRAY['frame_number','license_plate']`).

## Vehicle field purge — consequences staff and operators must know (08/10/2026)

- **The old history is gone by design, not lost to a bug.** Migration `20261008000300` deletes every row in `audit_logs`, `vehicle_activity`, `notifications`, `customer_communications` and `message_outbox`. From the moment it is applied there is no before/after trail for anything recorded earlier, so any dispute about a past transaction has to be settled from the surviving tables (`vehicles`, `acquisitions`, `sales`, `sale_financials`, `payments`, `payment_receipts`, `vehicle_expenses`) — not from the activity feed. New events are still audited and still raise notifications normally.
- **Old clients fail closed, they do not degrade.** A PWA bundle built before the purge sends no `vehicle_type_id`; the server answers `VEHICLE_TYPE_REQUIRED` and the write never happens. The same applies to saved shorthand/CSV files in the old shape. The mitigation is a fresh deploy plus the deliberate draft-key bump (`xe_crm_draft_v2`, `xe_crm_ux_v3`), which drops locally stored drafts that still carry purged fields instead of reloading them.
- **Every existing vehicle starts in `Chưa phân loại` and there is no bulk-classification screen.** Reclassification is manual, one file at a time, from the edit form. Until staff do it, the vehicle-type filter in **Kho xe** and the showroom type filter sort most of the inventory into that single bucket. Expected: `list_vehicle_types` reports a large `vehicle_count` on the fallback row for a while.
- **The public showroom now prints the chassis number** (`biển số · số khung`) because the requirement was identity consistency across every screen. This is a deliberate trade-off with a real risk: a visitor can copy enough of a file to forge a claim of ownership. If the owner prefers plate-only on the public page, it is a one-parameter change inside the shared display helper on the showroom read path — not a redesign.
- **There is no price anywhere in the system for an unsold vehicle**, by decision rather than omission: `sale_price` originates only from the Bán xe form and is never prefilled, and `asking_price` no longer exists as a column. Staff cannot look up "what were we asking for this bike", and the showroom shows no price block. The customer-submitted `expected_price` on "Định giá xe cần bán" is the only price-like figure on the public side, and it is customer-declared, never a shop price.
- **`operation_receipts` rows written before the purge are idempotency ghosts only.** Replaying an old saved request through a rebuilt RPC reports `OPERATION_REQUEST_CONFLICT` rather than re-running the write; that is the intended fail-closed behavior, but it means an operator cannot "resend" a pre-purge request and must re-enter it.
- Deno is not installed on the current workstation, so `node scripts/check-edge-native.mjs` cannot run locally (it fails with `spawn deno ENOENT`, which is an environment gap, not a code failure). `check-edge-types.mjs` passes with local platform types; native edge resolution must be verified before any function deploy.
